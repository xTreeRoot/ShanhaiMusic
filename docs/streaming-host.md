# 山海宿主 App：音视频断点流播改造方案

配套文档：[插件改造方案](streaming-plugins.md)。这是实施方案，不代表功能已上线。覆盖桌面、iOS 和 Android；Android 基线指当前工作区实现。首版验收音频五家、视频三家：内置 B 站、YouTube Music、网易云公开 MV。

## 1. 首版交付什么

| 用户动作 | 首版行为 |
| --- | --- |
| 从头播放 | 先取媒体头、索引与起播所需数据，不等整份文件；不支持按需读取时走明确的降级。 |
| 拖到未缓冲位置 | 取消被取代的请求，按目标时间取相关分段；主视频的画面和声音一起就位。 |
| 播放中断网或地址过期 | 保留曲目、毫秒位置和播放意图；网络恢复后补读，必要时重新向音源解析地址。不能安全拼接旧字节时，重新从同一时间点加载。 |
| 重启 App | 沿用当前队列和播放位置持久化，恢复为暂停；用户播放或打开画面时再取新地址，不自动弹出视频窗口。 |

**暂不做**跨重启保留未完成媒体分段、跨设备进度同步、平台云端进度回写、后台完整视频下载、自动切清晰度，也不新增 HLS/DASH 清单播放器。B 站当前给的是单独的 DASH 音轨和视频轨直链，不需要为它另建清单解析器。原有离线下载、完整缓存与上游插件兼容性不能退化。

## 2. 先改取流，不换播放器

**保留现有契约。** 桌面沿用 `music.Source.Stream` / `music.VideoSource.Video`，插件继续导出 `stream({id, quality})` / `video({id, quality})`。两者继续返回媒体 URL 和请求头；音频原有格式、大小等元数据照常使用。宿主按实际响应探测 Range，不增加 `seek`、`downloadChunk`、`resume` 之类的插件方法。只有 CDN 地址确实无法通过现有调用刷新时，再评估可选扩展。

### 分段读取与缓存规则

- 尝试按需读取时直接用小范围 `GET`，不把 `HEAD`、`Accept-Ranges` 或 URL 后缀当作成功凭证。只在 `206`、`Content-Range` 的起点、终点、总长和实际字节数能对上时，将响应交给那段读取。使用稳定的字节表示，不能混用解压前后的偏移。
- Range 收到 `200`，视为服务端忽略分段或条件不匹配，绝不把响应追加到非零偏移。走可取消的顺序读取；容器或原生引擎必须拿整文件时，只有在大小和磁盘预算允许时才用临时完整文件，否则明确提示无法跳读，视频可退回听歌。`416` 先核对范围与最新总长：已知 EOF 正常结束，有不一致则重新探测，不死循环。
- 已读区间和正在读取的区间按媒体对象隔离，合并重叠请求，限制并发、空间和前读。分段缓存先只在当前播放会话内保留；缓存与完整离线文件分开，只有确认字节覆盖完整才进入现有完整缓存。桌面主画面、迷你窗口和状态栏若并行取同一视频，尽量共享取流，不另开一套下载。
- 对同一已确认的资源，恢复时用强验证器等证据校验旧字节，可用时发 `If-Range`。曲目 ID、相同长度、格式或新旧地址看起来相似，都不足以证明字节相同。换链默认不拼旧字节，除非有可靠的同一媒体表示证据；换清晰度、编码、音频版本或授权范围必须隔离缓存。详见 [RFC 9110：Range Requests](https://www.rfc-editor.org/rfc/rfc9110.html#section-14) 和 [Combining Parts](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.7.3)。
- 短暂失败有限退避重试；疑似签名失效的媒体请求可重新解析同一曲目、同一档位一次，不能把所有 `403` 都当作过期。权限拒绝、无完整媒体或重试耗尽应保留原位置并给出手动重试，不循环续签，也不跳下一首。日志只留状态、区间和计数，不写签名 URL、Cookie 或授权头。

### 容器定位，不按时长比例切字节

普通 MP4/M4A 先取容器索引，允许跳到文件尾读元数据；分片 MP4 读取初始化和可用的分片索引。视频从目标附近可解码的关键帧开始，再呈现目标时刻；不是直接展示关键帧当作跳转完成。MP3/VBR、裸 AAC、FLAC 各自验证帧定位或索引能力；没有可靠索引的素材保留顺序流播与已缓冲区定位，不承诺任意位置秒跳。现有解码器和字幕时间轴继续使用。

## 3. 一个时间点，两条轨一起恢复

1. **播放协调器记一个目标。** 区分用户想播放、引擎正在播放、以及为缓冲暂时暂停。显式拖动或重新加载分配新代次；切歌、切音源、退出视频态、再次拖动时取消旧任务，晚到的首帧、错误和重试都不能改写新会话。暂停时拖动要出目标画面，但不能自动开播。
2. **主视频一起等，状态栏不跟着卡。** 现有音频是主时钟，视频静音。进入主视频、显式跳转或主视频持续缺数据时，先冻结共享时间点；音频可播且目标画面就绪后按原意图继续。轻微漂移沿用现有同步策略，不反复触发大跳转。视频不可用时可重试或切回听歌；状态栏预览仍只是跟随者，卡住不暂停音乐。用户主动暂停或系统打断后不擅自恢复。
3. **区分分轨和同容器。** B 站等独立 A/V 资源分别解析、分别取段，时间目标相同。对网易云这类音画使用同一资源的 MV，优先避免重复下载；确认两个读取者用的是同一媒体表示和授权范围后，再共享分段。若后续改为原生引擎一次解封装两条轨，必须接回原有队列、字幕、系统媒体控制和音量行为。任何模式都只能有一条实际出声的音轨。

## 4. 三端改动落点

| 端 | 现有实现 | 要改的地方 |
| --- | --- | --- |
| **桌面 Go/MyGo** | [`stream.go`](../internal/player/stream.go) 顺序下载；[`decoded.go`](../internal/player/decoded.go) 读未到字节会等前缀；[`mv_proxy.go`](../internal/app/mv_proxy.go) 已透传 Range 和媒体头。 | 先让 `internal/player` 的远程读取能按索引抓未到区间，同时保留顺序回退与完整缓存。沿用 [`mv.go`](../internal/app/mv.go) 的原生视频引擎和代理，给代理接相同的区间校验与错误传递，在播放协调层统一重取地址和双轨就绪。状态栏复用取流能力，不参与主视频暂停。逐个验证 macOS、Windows、Linux 后端，不能把 macOS 的结果算到另外两个系统。 |
| **iOS** | [`RemoteMediaAsset.swift`](https://github.com/xTreeRoot/ShanhaiMusic/blob/ios/ios/Sources/MBFoundation/RemoteMediaAsset.swift) 已为音视频分段读取；[`PlaybackModel.swift`](https://github.com/xTreeRoot/ShanhaiMusic/blob/ios/ios/Sources/MBFoundation/PlaybackModel.swift) 有音频退回整文件的路径；[`VideoModel.swift`](https://github.com/xTreeRoot/ShanhaiMusic/blob/ios/ios/Sources/MBFoundation/VideoModel.swift) 已有静音视频同步。 | 在现有加载器补错误分类、分段重试、资源更新与相容的分段复用。播放和视频模型共享恢复位置、代次和缓冲状态，别只增大重试次数。现有完整音频缓存任务不能在弱网时无条件与首帧抢带宽；视频无 Range 的降级单独验收。 |
| **Android** | [`PlaybackService.kt`](https://github.com/xTreeRoot/ShanhaiMusic/blob/android/android/app/src/main/java/com/xtreeroot/mb/playback/PlaybackService.kt) 负责音频、解析和队列恢复；[`VideoStage.kt`](https://github.com/xTreeRoot/ShanhaiMusic/blob/android/android/app/src/main/java/com/xtreeroot/mb/ui/VideoStage.kt) 使用静音 Media3 渐进视频。 | 保留原生取流；把重试、地址缓存失效和双轨等待交给播放协调层，而不是放在 Compose 重组回调里。视频表面继续只负责展示和生命周期。确认切到小窗、退后台、退回听歌时旧数据源及时释放，音频服务与前后台行为不退化。 |

改动顺序：先跑通桌面音频跳读和 B 站主视频同步，再把同样的恢复行为接到 iOS、Android；用喜马拉雅长单集验证音频，再补齐 YouTube Music、网易云 MV、网易云普通/无损及汽水格式。保留平台策略在适配层，通用播放逻辑不判断插件 ID。

## 5. 验收清单

| 场景 | 判定 |
| --- | --- |
| 冷启动播放、直接拖到 80% | 用足够长的样本和限速服务，记录首音/首帧时间、目标就绪时间和请求区间。目标出声、出画前只拉索引与目标附近数据，没有先下载整个前缀。分别测 B 站双轨和网易云同容器。 |
| 主视频缓冲、播放中断线 | 人为中断音频或视频请求。恢复后不跳回开头、不重复出声；用带同步标记的测试片验证，建议首版门槛为恢复稳定后连续 5 秒音画偏差不超过 150 毫秒。状态栏卡顿不影响音频。 |
| 地址过期或媒体变了 | 用固定测试源返回过期错误、不同资源版本、错误 `Content-Range` 和 `200` / `416`。只有合法响应参与拼接；换资源保留时间点，不混入旧字节。 |
| 连拖、暂停、切歌、关闭 | 最后一次拖动生效；暂停不误恢复；切歌或关窗后旧请求取消；重启恢复暂停且不自己开视频。 |
| 真源和系统 | 五家音频、三家视频各跑实际非零位置读取和重连；B 站分轨、网易云公开 MV、YouTube 直链分别留证据。桌面各系统、iPhone/iPad、Android 各自记录结果，不拿模拟 CDN 回归当真机验收。 |

桌面用现有 `httptest`、播放器和 `ui.NewTester` 回归；提交前按仓库约定运行 `npm run test:plugins`、`CGO_ENABLED=0 go test ./...`、`go tool mygo vet .` 并构建核对桌面包。iOS 跑 Swift 行为回归和相关真机/模拟器构建测试，Android 跑对应 Gradle 回归和设备播放验证。当前已有桌面 Range 透传、Swift 视频行为回归，以及 B 站游客 `206` 和原生首帧证据；这些都不等于已验收两条轨的非零跳读和中途恢复。
